# План сборки первого прототипа

12 сентября 2026. Предложение для реализации в официальный период хакатона; код ещё не написан.

## Продукт и первый сценарий

“An AI referral manager that turns customer recommendations into bookings and purchases—all inside messaging apps.”

Общее ядро обслуживает рефералы бизнеса. Для первого демо предлагаем барбершоп: выбор услуги, мастера, времени и бонус после первого оплаченного визита. Первая ниша ещё требует выбора команды. Фитнес, школы, рестораны, клининг и детейлинг остаются направлениями расширения.

## Что собираем

1. Чат клиента: персональное приглашение, вопросы об услуге, доступное время, запись и статус собственного бонуса.
2. Небольшой кабинет бизнеса: услуги/мастера/слоты, правила программы, записи, подтверждение оплаченного визита, журнал наград.
3. Backend: проверка подключения и tenant, рефералы, бронирование, правила начисления, повторные события, отправка уведомлений.

Для прототипа предлагаем один TypeScript backend, PostgreSQL, простой web-кабинет и одну модель с tool calling через OpenRouter. Разделение на модули достаточно; отдельные микросервисы и собственный agent framework не нужны. Это выбор архитектуры, не результат сравнения производительности стеков.

## Канал

Если официальный WhatsApp-доступ уже работает, используем его. Если нет, первый сквозной сценарий показываем в Telegram и явно называем его Telegram-прототипом. Telegram поддерживает стартовые параметры в ссылках; используем короткий непрозрачный код приглашения, а не персональные данные. [Документация](https://core.telegram.org/bots/features#deep-linking).

Одного общего бота для демо достаточно, если после входа он явно показывает название бизнеса и разрешает сменить бизнес без смешения историй. Для production собственный номер/бот бизнеса — отдельный вариант подключения. Создание каждого номера автоматически не предполагается.

## Инструменты агента

| Действие | Результат | Ограничение |
|---|---|---|
| get_offer | Услуги, цены, правила бонуса | Только подтверждённые владельцем данные |
| create_invite | Ссылка/код для текущего клиента | Проверка участия в программе |
| get_available_slots | Мастер и свободное время | Только реальная база записи |
| book_visit | ID подтверждённой записи | Явное согласие клиента, повторная проверка слота |
| get_my_rewards | Баланс и статусы текущего клиента | Нет доступа к данным друга |
| handoff_to_staff | Передача вопроса администратору | Автоответы приостанавливаются на время ручной работы |

OpenRouter передаёт запрос модели на вызов инструмента; наш backend исполняет собственные инструменты и возвращает результат. [Tool calling](https://openrouter.ai/docs/guides/features/tool-calling).

Агенту не выдаём инструмент «считать визит оплаченным». Это отдельное действие авторизованного сотрудника либо доверенное событие кассы. При ошибке бронирования агент не сообщает об успехе. При конфликте слота предлагает другое время.

## Данные и правила

Минимальные сущности: businesses, channel_connections, customers, campaigns, referrals, services, staff, slots, bookings, conversion_events, reward_ledger, conversations, outgoing_notifications.

Это перечень ответственности, не требование создавать отдельную таблицу для каждого пункта. Везде, где есть данные бизнеса, права ограничены tenant. Входящее сообщение определяется по проверенному подключению; код приглашения проверяется сервером. Клиент не задаёт произвольный tenant через текст.

Запись создаётся атомарно: два клиента не занимают один слот. Визит и оплата имеют отдельные признаки. Реферальная связь фиксируется до конверсии по правилам программы. Вознаграждение требует подходящего первого оплаченного визита, допустимого участника и отсутствия предыдущего начисления за этот результат.

Подтверждение конверсии, проверка уникальности и запись награды выполняются в одной транзакции. Уведомление можно повторить после сбоя без повторного начисления. Отмена и исправление оставляют журнал; погашение бонуса — отдельная операция.

## Подключение существующего агента

Реферальное ядро предоставляет те же операции через API. Существующий агент вызывает их и сам отвечает пользователю; наш агент в таком режиме не отправляет параллельные ответы. Подключение требует поддержки внешних действий его платформой. Для первого демо достаточно нашего агента, API-контракт сохраняем для следующего подключения. MCP можно добавить позднее, если конкретный агент его требует.

## Роль Exa

Возможное последующее применение — помочь владельцу собрать черновик описания бизнеса по публичным источникам. Это необязательный onboarding; извлечённые сведения публикуются только после проверки владельцем. Для первого демо ручной ввод быстрее и надёжнее. Поиск не используется для определения свободных слотов, оплаты или правил бонуса.

## Порядок сборки

1. Создать тестовый бизнес, программу и учёт конверсий. Без AI проверить начисление, повтор события и отмену.
2. Подключить один мессенджер. Два человека проходят приглашение по коду; бизнес и реферер определяются правильно.
3. Добавить каталог, слоты и запись с защитой от двойного бронирования.
4. Добавить AI-инструменты, вопросы об услугах и явное подтверждение записи.
5. Добавить кабинет сотрудника, подтверждение оплаченного визита, баланс и доставку уведомлений.
6. Проверить сквозной путь и записать двухминутное демо. Ручное подтверждение и тестовая база обозначаются в видео.

## Приёмка

- Два клиентских аккаунта проходят приглашение → запись → оплаченный визит → бонус.
- Повтор сообщения или события не создаёт вторую запись/награду.
- Отменённая запись без оплаченного визита не создаёт бонус.
- Конкурентное бронирование одного слота даёт один успех.
- Пользователь не может прочитать баланс другого клиента или бизнеса.
- Сбой модели не меняет учёт; сбой уведомления не дублирует награду.
- Ни один ответ агента не подтверждает действие, которое backend не выполнил.

## Что проверяем после демо

Тезис: разговор сокращает работу администратора и помогает приглашённому записаться. Возражение: существующий бот плюс referral API может делать то же самое.

Ограниченный тест: один бизнес, несколько реальных приглашений с согласиями и сравнение с его обычным процессом. Продолжать при готовности бизнеса оплачивать пилот и наблюдаемом улучшении процесса. Менять подход, если достаточно интеграции с существующим ботом. Остановить реальные начисления при ошибках изоляции или учёта. Даже при неудаче остаются проверенные схемы событий, интервью и интеграционный контракт.
